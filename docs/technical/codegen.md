# Codegen

## Responsibility

Read the SQLite database and emit GDScript stub files that game developers
fill in to implement their bindings. Run as an editor tool (not at game
runtime). Validate that existing binding files match the current database
state and raise errors for mismatches.

---

## When to Run

Codegen runs manually via **Tools > Tarinoi: Regenerate Bindings**.

> **Not yet implemented:** automatic codegen after a successful sync
> (`tarinoi/codegen/on_sync` setting).

Codegen never runs at game runtime.

---

## Output Files

Files are written to the path configured in `tarinoi/codegen/output_path`
(default: `res://demo/bindings/generated/`). Configure this in Project Settings
to a path appropriate for your game (e.g. `res://bindings/generated/`).

| File | Contents |
|---|---|
| `tarinoi_functions.gd` | One inner class per function collection |
| `tarinoi_variables.gd` | One inner class per variable collection |
| `tarinoi_lists.gd` | Constants for all list option values |
| `tarinoi_entities.gd` | Constants for all entity names |

These files are stubs — they declare the interface but do not implement it.
Game developers copy or subclass them in `demo/bindings/impl/` and fill in
the logic. The generated files should be committed to version control and
regenerated whenever the Tarinoi project changes.

One more file is written to the *impl* directory (`tarinoi/codegen/impl_path`,
default `res://bindings/impl/`), and only once: the reference implementation of
Tarinoi's core functions. See "Core functions scaffold" below.

## `tarinoi_functions.gd`

One inner class per function collection. Each class has one method stub per
declared function.

```gdscript
# AUTO-GENERATED by Tarinoi codegen. Do not edit manually.
# Regenerate with: Tarinoi → Regenerate Bindings

class_name TarinoiFunctions

class TarinoiGlobalFunctions:
    ## MyFunnyGate(flag: bool) -> bool
    ## effect: pure
    func MyFunnyGate(flag: Variant) -> Variant:
        push_error("TarinoiFunctions.TarinoiGlobalFunctions.MyFunnyGate is not implemented")
        return false

class TarinoiChecksFunctions:
    ## SkillCheck(skill: Variant, threshold: Variant) -> bool
    ## effect: side-effect
    func SkillCheck(skill: Variant, threshold: Variant) -> Variant:
        push_error("TarinoiFunctions.TarinoiChecksFunctions.SkillCheck is not implemented")
        return false
```

**Notes:**
- Class names are `Tarinoi{PascalCollectionName}Functions` — see "Class Naming"
  below for why the bare collection name isn't used directly.
- Method names match `function_name` exactly (Tarinoi names are already
  PascalCase by convention).
- Argument names match `arg_name` from `TArgDeclaration`.
- All arguments are typed `Variant` in the stub because the game receives
  resolved values (the Dispatcher resolves `Ls`, `Var`, `Ent` references
  before calling). The declared `data_type` is included as a comment.
- Return type is `Variant` for the same reason; declared `function_returns`
  is in a comment.
- `push_error` in the body ensures unimplemented stubs are loud.

## `tarinoi_variables.gd`

One inner class per variable collection. Each declared variable becomes a
real, typed `var` field with its Tarinoi default value; `get_variable` /
`set_variable` are implemented in terms of those fields via Godot's built-in
`Object.get()` / `Object.set()` reflection.

```gdscript
# AUTO-GENERATED by Tarinoi codegen. Do not edit manually.

class_name TarinoiVariables

class TarinoiPlayerVariables:
    var health: float = 100.0
    var has_keycard: bool = false

    func get_variable(variable_name: String) -> Variant:
        return get(variable_name)

    func set_variable(variable_name: String, value: Variant) -> void:
        set(variable_name, value)
```

**Data type mapping** (`TVariableDeclaration.data_type` → GDScript field type):

| Tarinoi `data_type` | GDScript type |
|---|---|
| `boolean` | `bool` |
| `number` | `float` |
| `string` | `String` |

A variable with no `default_value` declared falls back to the type's zero
value (`false` / `0.0` / `""`).

**Why fields instead of comments.** A pass-through implementation needs no
code beyond `extends TarinoiVariables.TarinoiPlayerVariables` — the fields are
inherited with their defaults already set, so there is nothing for the
developer to hand-copy or keep in sync. Because the fields are real and typed,
referencing a variable that Tarinoi has since renamed or removed
(`.has_keycard`) is a genuine GDScript parse error in the editor — not a
silent runtime mismatch. This is the same interface-vs-implementation split
the `extends TarinoiFunctions.*` convention already gives function bindings
(see above), now applied to variables.

Implementations with a custom backing store (savegame system, blackboard)
override `get_variable` / `set_variable` directly and call `super` for
variables they don't special-case:

```gdscript
class_name GlobalVariables
extends TarinoiVariables.TarinoiGlobalVariables

func get_variable(variable_name: String) -> Variant:
    if variable_name == "pc_health":
        return SaveSystem.player.health
    return super.get_variable(variable_name)

func set_variable(variable_name: String, value: Variant) -> void:
    if variable_name == "pc_health":
        SaveSystem.player.health = value
        return
    super.set_variable(variable_name, value)
```

Custom-cased variables like `pc_health` above are still matched by name as a
string, so renames in Tarinoi won't be caught by the GDScript parser for
that branch — mismatch validation (below) is the safety net for those cases.

---

`COLLECTIONS` maps every collection identifier to its generated class, so a
game — or the quickstart scene — can bind them all without naming each:

```gdscript
for col in TarinoiVariables.COLLECTIONS:
    TarinoiRuntime.registry.bind_variable_collection(col, TarinoiVariables.COLLECTIONS[col].new())
```

## Core functions scaffold

Tarinoi ships a fixed set of **core functions** — `Fn.tarinoi.*`: `SetFlag`,
`ClearFlag`, `ToggleFlag`, `SetCounter`, `IncrementCounter`, `SetText`,
`FlagIsSet`, `NumberEquals`, `NumberAtLeast`, `NumberGreaterThan`,
`NumberAtMost`, `NumberLessThan`, `StringEquals` — that in-app playback
evaluates for real. The plugin has to implement them with the same semantics,
and the game may want to change *how* (a different variable store, savegame
hooks). So the implementation is generated, once, as the game's own code.

When the synced project has a function collection whose identifier is
`tarinoi`, `run()` writes `tarinoi_core_functions.gd` into the impl directory
**if no such file exists**:

```gdscript
# Tarinoi core functions 0.0.1 — reference implementation.
# Scaffolded by Tarinoi codegen from <api_path>.
#
# This file is yours: edit it freely, codegen never overwrites it. Delete it
# to get a fresh copy the next time you regenerate bindings.
class_name TarinoiCoreFunctions
extends TarinoiFunctions.TarinoiTarinoiFunctions


## Set a flag.
func SetFlag(flagRef: Variant) -> Variant:
    _write(flagRef, true)
    return null
…
```

The rendering lives in `TarinoiCoreFunctionsScaffold`
(`addons/tarinoi/codegen/core_functions.gd`): a table of the thirteen bodies,
keyed by name, plus the four helpers (`_write`, `_flag`, `_number`, `_text`)
they call. The helpers encode the contract shared with playback:

- A `Var.*` argument arrives as a `VarRef`; `_write` writes through it and
  logs if handed anything else.
- Reads resolve a `VarRef` and pass plain values (literals, list items — the
  Dispatcher has already resolved `Ls.*`) through.
- **Unset variables read as `false` / `0` / `""`.** This is the part an
  author relies on: what they verified in playback must hold in the game.
- A value of the wrong type is an authoring error. Playback throws; the game
  logs via `TarinoiLogger.error` and uses the type's default, because a
  running dialogue should not crash over it.

Rules:

- The collection must be called exactly `tarinoi`. A project still carrying
  the pre-rename `core` collection gets ordinary stubs for it, matching the
  app, which no longer treats that collection as core either.
- A declaration in the collection matches a body by **name and arity**.
  Anything else — a newer app added a function, an arity changed — gets the
  usual not-implemented stub, and codegen warns naming it.
- The scaffold's first line stamps the version of the set it was rendered
  from (`TarinoiCoreFunctionsScaffold.VERSION`, which follows the public core
  functions document).

Validation (`run()` and `validate_only()`) checks an existing scaffold and
reports **warnings only** — it is the game's code, and a missing method still
falls through to the generated base class stub:

| Condition | Message |
|---|---|
| Scaffold exists, project has no `tarinoi` collection | `Core functions scaffold … exists but the project has no 'tarinoi' collection — delete it, or recreate the core functions in Tarinoi` |
| Stamp differs from the plugin's version | `Core functions scaffold … is version '0.0.0'; this plugin scaffolds 0.0.1 — delete it to re-scaffold, or merge the changes by hand` |
| A synced `tarinoi.*` function has no method in the scaffold | `Core functions scaffold … has no 'X' — Fn.tarinoi.X will hit the not-implemented stub; …` |
| Method arity differs from the declaration | `Arg count mismatch in core functions scaffold 'X': DB=2 scaffold=1` |

Binding it is one line, and the quickstart scene does it for you:

```gdscript
TarinoiRuntime.registry.bind_function_collection("tarinoi", TarinoiCoreFunctions.new())
```

`TarinoiQuickStart._ready()` calls `_bind_generated_defaults()` after
`_setup_bindings()`: any variable collection in `TarinoiVariables.COLLECTIONS`
left unbound gets its generated class, and `tarinoi` left unbound gets
`TarinoiCoreFunctions`, both looked up through the global class list so the
plugin never references the game's generated code directly. A real game binds
explicitly; the convenience belongs to the quickstart scene, not the runtime.

## Class Naming

Every generated inner class (per function collection, per variable
collection, per list collection, per list, per entity collection) is named
`Tarinoi{PascalCollectionName}{Kind}` — e.g. `TarinoiPlayerVariables`,
`TarinoiChecksFunctions`, `TarinoiSkillsList`, `TarinoiMajorEntities`.

This is more verbose than the bare collection name (`Player`, `Checks`), and
it needs to be: Godot's `class_name` global-class registry rejects **any**
class declaration — including one nested inside an unrelated wrapper class in
a completely different script — whose name matches an existing global
`class_name` elsewhere in the project (`Parse Error: Class "X" hides a global
script class`). Nesting under `TarinoiVariables`/`TarinoiFunctions`/etc. does
not protect a bare collection name from this: a Tarinoi `player` variable
collection generating a nested class named plain `Player` will fail to parse
the moment the consuming game also has its own `class_name Player` (a
character controller, for instance) anywhere in the project — which is common,
since collection identifiers are often ordinary nouns.

This is a Godot-specific limitation, not a general engine constraint —
nested classes in Unity (C#) resolve purely through lexical/namespace scoping
and never collide with an unrelated top-level class of the same bare name.
Rather than requiring globally-unique collection identifiers in Tarinoi itself
(which would encode a Godot quirk into the cross-engine data model), the
`Tarinoi`-prefixed, kind-suffixed name keeps the constraint local to the Godot
codegen output.

## `tarinoi_lists.gd`

Constants for all list options, enabling game code to use symbolic names
rather than raw strings when interacting with list values.

```gdscript
# AUTO-GENERATED by Tarinoi codegen. Do not edit manually.

class_name TarinoiLists

class TarinoiPlayerLists:
    class TarinoiSkillsList:
        const MECHANICS = "mechanics"
        const RHETORIC  = "rhetoric"
        const EMPATHY   = "empathy"

class TarinoiGlobalLists:
    class TarinoiThresholdsList:
        const TRIVIAL      = "trivial"
        const EASY         = "easy"
        const CHALLENGING  = "challenging"
        const FORMIDABLE   = "formidable"
```

`TarinoiLists.TarinoiPlayerLists.TarinoiSkillsList.MECHANICS` is the canonical
way for game code to reference list values. The actual `option_value` (from
`TListOptionSpec`) is stored in the DB and resolved by the Dispatcher at
runtime; these constants match the `key` field.

---

## `tarinoi_entities.gd`

Constants for all entity names, enabling symbolic references in game code.

```gdscript
# AUTO-GENERATED by Tarinoi codegen. Do not edit manually.

class_name TarinoiEntities

class TarinoiMajorEntities:
    const SYLVIA_WHISTLER  = "sylvia_whistler"
    const IRMA             = "irma"

class TarinoiSupportingEntities:
    const UNNAMED_GUARD    = "unnamed_guard"
```

Constants are the `entity_name` from `TEntity.entity_name`, uppercased with
underscores. Class names follow the `Tarinoi{PascalCollectionName}Entities`
scheme described above.

## Mismatch Validation

Codegen compares the current database state against any previously generated
files. Mismatches are logged to the Godot editor Output panel via
`push_error()` / `push_warning()`.

### Mismatch Conditions (implemented)

Validation operates at the **class/collection level** for functions, and at
the **per-variable field level** for variables (name and type). List/entity
validation and collection renames are not yet implemented.

| Condition | Severity | Message |
|---|---|---|
| Function class in DB not in generated file | ERROR | `Missing function class 'TarinoiChecksFunctions' — regenerate` |
| Function in DB not in generated file | ERROR | `Missing function 'TarinoiChecksFunctions.SkillCheck' — regenerate` |
| Function argument count changed | ERROR | `Arg count mismatch 'TarinoiChecksFunctions.SkillCheck': DB=2 generated=3 — regenerate` |
| Function class in generated file not in DB | WARNING | `Obsolete function class 'TarinoiChecksFunctions' — remove from impl` |
| Function in generated file not in DB | WARNING | `Obsolete function stub 'TarinoiChecksFunctions.OldFunction' — remove from impl` |
| Variable class in DB not in generated file | ERROR | `Missing variable class 'TarinoiPlayerVariables' — regenerate` |
| Variable in DB not in generated file | ERROR | `Missing variable 'TarinoiPlayerVariables.has_keycard' — regenerate` |
| Variable field type changed | ERROR | `Type mismatch 'TarinoiPlayerVariables.persuasion_score': DB=float generated=bool — regenerate` |
| Variable class in generated file not in DB | WARNING | `Obsolete variable class 'TarinoiPlayerVariables' — remove from impl` |
| Variable in generated file not in DB | WARNING | `Obsolete variable 'TarinoiPlayerVariables.old_field' — remove from impl` |

> **Not yet implemented:** list option changes, entity changes, collection
> renames.
>
> Note that most variable drift is now caught for free by the GDScript
> parser itself (see "Why fields instead of comments" above) — this table
> mainly still matters for variables re-implemented with a custom
> `get_variable` / `set_variable` override, where the Tarinoi name is matched
> as a string rather than a real field reference.

ERRORs block codegen from completing (files are not written).
WARNINGs are logged but codegen proceeds.

### Validation Flow

```
1. Read all TFunctionDeclaration, TVariableDeclaration, TListSpec, TEntity
   documents from SQLite.
2. If generated files exist, parse them (regex/line scan — not full GDScript
   parse, just extract class names and method signatures).
3. Compare. Collect errors and warnings.
4. If errors: log all, abort, do not write files.
5. If warnings only: log all, write files (regenerating updates the stubs).
6. If no issues: write files silently.
```

## Codegen Algorithm

### Querying the Database

Each declaration type is joined against the *collection's own
`collection-manifest` document* (not the `collections` table) to resolve its
machine identifier:

```gdscript
# Functions (variables, lists, and entities follow the same shape)
SELECT d.identifier, d.payload, cm.identifier AS col_name
FROM documents d
JOIN documents cm ON cm.document_id = d.collection_id
                 AND cm.document_type = 'collection-manifest'
WHERE d.document_type = 'function-declaration'
  AND <active_filter on d>
ORDER BY col_name, d.identifier
```

**Why the self-join instead of the `collections` table:** the `collections`
table's `collection_name` column (and the equivalent key in its JSON payload)
holds the collection's human-entered **display label** (e.g. "Global
functions"), not its snake_case machine identifier. The actual identifier
(`global`, `player`, …) lives on the `identifier` column of the collection's
own row in `documents`, where `document_id == collection_id` and
`document_type == 'collection-manifest'`. Resolving the label instead of the
identifier silently produces no results at all (the label never matches
anything downstream) rather than a visible error — this is worth getting
right the first time.

Entities additionally filter on `json_extract(d.payload, '$.dialog_capable') = 1`.

Each declaration's own payload uses `list_options` (not `options`) for a
list-spec's option array — see `document.d.ts`'s `TListSpec`.

### Collection Identifier to Class Name

```gdscript
static func _to_pascal(s: String) -> String:
    # "player_state" → "PlayerState"
    var parts := s.split("_")
    var result := ""
    for p in parts:
        if not p.is_empty():
            result += p[0].to_upper() + p.substr(1)
    return result

# "player" + "Variables" → "TarinoiPlayerVariables" — see "Class Naming" above
# for why the bare PascalCased identifier isn't used directly.
static func _collection_class_name(name: String, kind: String) -> String:
    return "Tarinoi%s%s" % [_to_pascal(name), kind]
```

### Entity Name to Constant Name

```gdscript
func entity_name_to_const(name: String) -> String:
    # "sylvia_whistler" → "SYLVIA_WHISTLER"
    return name.to_upper()
```

## Editor Integration

The codegen is invoked from an `EditorPlugin` that adds a Tarinoi menu to
the editor toolbar:

```
Tarinoi
  └── Sync Now
  └── Regenerate Bindings
  └── Validate Bindings
  └── Plugin Settings...
```

"Validate Bindings" runs the mismatch check without writing files — useful
for CI or pre-commit checks via `godot --headless --script`.
